# CLAUDE.md

Guide pour Claude Code sur ce dépôt : API REST PHP 8 de la « Tour de contrôle NavUp » (outil interne de NavUp Academy).
Front Angular 21 : `~/Documents/_DEV/navup-front`. Cahier des charges : `~/Documents/nabil/Cahier_des_charges_Tour_de_controle_NavUp.pdf`.
Architecture de référence : `/var/www/manicarton-api` (même style maison). L'appli des parents est un autre projet (`/var/www/navup-parent-api`).

## Feuille de route

Livraison par étapes, un plan par étape : 1 socle et authentification (fait), 2 prospects, clients et fiche 360° (fait), 3 ventes, paiements et échéancier (fait), 4 rendez-vous, appels et tâches (fait), 5 tableau de bord (fait), 6a formation et chaîne de vente (fait : gestion de la formation, e-mails aux parents, Stripe, compte NavUp Academy et programme, supervision des connexions), appli des parents, première livraison (fait : `/var/www/navup-parent-api` et `~/Documents/_DEV/navup-parent-front` ; page publique avec achat, accès par lien, programme, sujet, progression ; côté Tour : fin de l'accès, liens d'accès, invitation, pages des fiches en images), 6b rendez-vous en ligne (fait : disponibilités et créneaux, rendez-vous découverte pris sur la page publique, rendez-vous d'accompagnement pris depuis l'espace des parents, lien pour annuler ou déplacer, e-mails de rendez-vous avec invitation `.ics`, rappel, flux d'agenda), 7a statistiques, exports et rapport (fait : page des statistiques, exports Excel des listes, export comptable, rapport PDF), 7b alertes réglables, paramètres, modèles d'e-mails, vues enregistrées (fait), 8 sécurité et mise en production (fait : double authentification facultative, RGPD — effacement proposé, confirmé par l'administrateur, données et suppression côté parents —, sauvegardes chiffrées et restauration prouvée, en-têtes de sécurité, `deploiement/` ; le déploiement lui-même attend le choix de l'hébergement).

## Architecture

- **Pas de framework, pas de composer, pas d'autoload** : includes manuels, exécution directe par php-fpm.
- **Un dossier par ressource** : `v1/<ressource>/index.php` (sous-ressources : `v1/<ressource>/<action>/index.php`).
  L'URL locale est `http://localhost/navup-api/v1/<ressource>/` (DocumentRoot Apache = `/var/www`).
- `include/` : classes partagées (`package.*.php`). `api/` : bibliothèques tierces embarquées. `api/stripe/` est le SDK officiel `stripe-php` 20.1.0, copié tel quel et chargé par `require api/stripe/init.php` (version d'API `2026-04-22.dahlia`) : on ne le modifie pas, on le remplace en bloc.
- `require/param.php` : réglages versionnés, sans secret (délais des prélèvements, durée d'un lien de paiement, modalités de l'achat en ligne, versions des CGV, seuils des limiteurs, tailles des médias). Il charge `require/secret.php` (hors dépôt, modèle `secret.exemple.php`) : `$_PROD`, `$_DB`, `$_CORS_ORIGINES`, `$_MAIL_ERREUR`, et depuis l'étape 6a les clés Stripe, le mode des e-mails (`$_MAIL_MODE` : `essai` ou `reel`), les origines des pages publiques, les adresses (`$_URL_TOUR`, `$_URL_RETOUR_PAIEMENT`, `$_APP_PARENTS_URL`), le dossier des médias et les chemins de `ffmpeg`. Ne jamais lire ni afficher `secret.php` : le compléter par ajout.
- `sql/` : DDL numérotés (`000_`, `001_`…), appliqués à la main avec `mariadb -unavup -p navup < sql/…`. `script-cgi/` : scripts CLI.
- `.htaccess` bloque en HTTP `.git`, `include/`, `api/`, `require/`, `sql/`, `script-cgi/`, les fichiers cachés et les `.sql .md .log`.
- **Tâche planifiée** : `script-cgi/planifie.php`, à brancher sur cron toutes les 15 minutes. Sans elle, ni prélèvement, ni e-mail à date, ni conversion audio, ni fin de programme. Une passe par sous-processus (`Mysql::Erreur()` fait `exit` : une erreur SQL ne doit pas emporter les passes suivantes), un seul exemplaire à la fois (`GET_LOCK`), dernier passage de chaque passe dans `t_planifie`.
- **Médias de la formation** : hors du dépôt et hors du web, dans `$_DOSSIER_MEDIAS` (`/var/www/navup-media`), accessibles en écriture à php-fpm et à l'utilisateur de la tâche planifiée. Fichiers à plat, nommés par leur empreinte SHA-256, jamais servis par Apache (`Formation::dossier()` y pose un `.htaccess` de refus).
- **Endpoints sans utilisateur** : `v1/public/` (achat en ligne, lien de paiement, retour de Stripe, créneaux et rendez-vous en ligne), `v1/agenda/flux/` (calendrier abonné) et `v1/stripe/webhook/`. Ils démarrent par `Automate::demarrer()` au lieu d'instancier les classes une à une.

## Pattern d'un endpoint

```php
<?php
include "../../include/package.header.php";
include "../../include/package.mysql.php";
include "../../include/package.data.php";
include "../../include/package.response.php";
include "../../include/package.user.php";
include "../../require/param.php";

$H = new Header();
$H->cors('json');                 // CORS + réponse au préflight OPTIONS (exit)

$Response = new Response();
$CD = new ControleData();
$U = new User();

$Mysql = new Mysql();
$SQL = $Mysql->OuvrirBase();      // mysqli, identifiants lus dans $_DB

$file_err = getcwd() . "/index.php";
date_default_timezone_set('Europe/Paris');

if ($_SERVER['REQUEST_METHOD'] === "GET") {
    $user = $U->requireAccess('clients', 'L');   // 401/403 automatiques
    $rows = $Mysql->fetchAll("SELECT ... WHERE actif = ?", array(1), 'i');
    $Response->success(array('clients' => $rows));
}

$Response->methodNotAllowed();
```

Les noms de variables globales comptent : les classes les lisent par `global` (`$SQL`, `$file_err`, `$Mysql`, `$H`, `$Response`, `$CD`, et les réglages de `param.php`).
Corps JSON : `$R = json_decode(file_get_contents("php://input"));`. Toujours vérifier `isset()` + type avant usage.

## Classes partagées

- `Mysql` (`package.mysql.php`) — **requêtes préparées obligatoires** : `fetchOne`, `fetchAll`, `execute`, `lastId`, `prepared`. Toute erreur SQL passe par `Erreur()` : mail à `$_MAIL_ERREUR` (sans valeurs liées), HTTP 500 générique préfixé, `exit()`.
- `Response` (`package.response.php`) — `success($data, $status)`, `validationError` 400/code 1, `authError` 401/code 2, `tokenExpired` 401/code 301, `forbidden` 403/code 3, `notFound` 404, `methodNotAllowed` 405, `rateLimitExceeded` 429. Chaque méthode envoie le JSON préfixé `)]}',` et fait `exit()`.
- `Header` (`package.header.php`) — `cors('json')` (localhost en développement, hôtes de `$_CORS_ORIGINES` en production, 403 sinon ; un endpoint public passe sa propre liste : `cors('json', $_CORS_ORIGINES_PUBLIQUES)`), `getBearerToken()` (décode `base64(sel7 + token + sel4)`), `cors_stripe()` (filtre IP des webhooks ; la signature Stripe reste la vraie authentification).
- `User` (`package.user.php`) — `requireUser()`, `requireAccess($module, 'L'|'C')`, `requireProfil([...])`, `can()`, `User::MATRICE`, `audit($id_users, $action, $details, $cible_type, $cible_id)`, `checkPasswordPolicy()`, `decodePassword()`, `creerToken()` (renvoie le jeton brut, stocke son empreinte), `publicUser()`, `adminUser()`, `validerChamps()`, `verifierUnicite()`, `motDePasseFourni()`, `genererMotDePasse()`, `compterAdminsActifs()`, throttle IP (`checkIpThrottle`, `noteIpFailure`, `clearIpFailures`).
- `ControleData` (`package.data.php`) — `clean_text($str, array('API'))` pour toute valeur texte courte, `array('EMAIL')`, `gen_token()`.
- `Saisie` (`package.saisie.php`) — lecture d'un corps JSON d'après une spécification : `lireChamps($R, $specs, $partiel)` (types `str`, `text`, `int`, `bool`, `enum`, `email`, `tel`, `date`, `heure`, `fk` ; longueur maximale obligatoire, valeur vide rendue `null`, 400 au premier champ invalide), `lireCle($R)` (clé de saisie d'un formulaire), `dateFiltre($cle)`, `verifierUnique()`, `pagination()`, `tri($autorises, $defaut, $departage)`, `inserer()`, `mettreAJour()`, `differences($actuel, &$data)` (noms des champs modifiés, jamais leurs valeurs). Les types `str` et `text` ne passent pas par `strip_tags`.
- `Contact` (`package.contact.php`) — dossiers : `Contact::STATUTS`, `Contact::GROUPES`, `groupeDe()`, `reference()`, `exigerDossier($id, $niveau)` et `exigerFamille($id, $niveau)` (le droit dépend du statut du dossier : ils chargent la ligne puis vérifient), `sortie()`, spécifications de saisie (`specContact()`, `specDeclaration()`, `specEnfant()`, `specProblematique()`), `conditionRecherche($q)`, `conditionLisibles($user)`, `verrouiller($id)` (transaction et verrou du dossier, pour toute écriture qui le concerne), `tracer()` (audit et chronologie ; `date` : la date du fait quand ce n'est pas celle de la saisie), `changerStatut()`, `famille($id)`, `chronologie(…, $avecFamille)` (les textes internes ne sont lus qu'avec le droit famille). Un endpoint de dossier inclut `package.saisie.php` et `package.contact.php` après `package.user.php`, et instancie `$S` puis `$Contact`.
- `Vente` (`package.vente.php`) — ventes et paiements : `exigerVente($id, $module, $niveau)`, `sortie()`, `echeances()`, `paiements()`, `historique()`, `blocDossier()`, filtres des listes (`conditionDossiersLisibles()`, `conditionRecherche()`, fragments `SQL_SOMMES`, `SQL_VENDU`, `SQL_RESTE`, `SQL_EN_COURS`), `calculer()` (statut et échéances d'après le grand livre, sans rien écrire), `recalculer()` (seul point d'écriture des caches), et les écritures : `creer()`, `ecrire()`, `annulerEcriture()`, `corrigerEcriture()`, `modifier()`, `reviserEcheancier()`, `annuler()`. Elles prennent l'auteur et l'origine : Stripe écrit par les mêmes méthodes (`creer(…, $origine, $stripe)` et `ecrire()` refusent un `stripe_id` déjà écrit, sous le verrou du dossier). Côté Stripe : `echeancier($total, $n, $debut)` (pendant PHP de `proposerEcheancier` du front), `enregistrerCarte()`, `noterClientStripe()`, `reglerPrelevement()` (actif, suspendu), `fermerSessions()`, `exigerSansPrelevement()` (révision et annulation refusées tant qu'un prélèvement est en cours), `lienStripe()` (adresse du tableau de bord Stripe d'une écriture). `automatismes()` ouvre le compte NavUp Academy au premier encaissement et passe le dossier en `client_actif` ; il désactive le compte quand la vente est défaite. ## Règles

- **Interdits** : interpolation de variables dans une requête SQL, `rand()` pour des secrets, presets `clean_text` `DEFAULT`/`TOUT`/`MYSQL` sur une valeur liée (ils font `addslashes`), tout secret dans un fichier versionné.
- **Texte libre** (notes, comptes rendus, objectifs du parent) : ne pas passer par `clean_text('API')`, qui applique `strip_tags` et supprime tout ce qui ressemble à une balise (« enfant <10 ans, note >5 » devient « enfant 5 »). Contrôler la longueur, lier la valeur telle quelle, et laisser l'échappement à l'affichage.
- Ne jamais nettoyer ni tronquer un mot de passe ; hachage `password_hash(PASSWORD_BCRYPT)` / `password_verify` uniquement.
- Compatibilité PHP 8.2+ : pas de syntaxe 8.4+.
- Tables préfixées par domaine : `u_` utilisateurs, sessions, audit ; `d_` dossiers (contact, déclaration, enfant, problématique, note, événement) ; `v_` ventes (vente, échéance, paiement, historique) ; `r_` rendez-vous ; `i_` interactions (appels et autres échanges) ; `t_` tâches et leur synchronisation ; `p_` listes de référence ; `f_` formation (semaines, sujets, fichiers) ; `a_` comptes NavUp Academy ; `s_` Stripe (commandes, sessions, liens, prélèvements, signaux) ; `m_` e-mails. Les préfixes des autres domaines se fixent à l'étape qui les crée. InnoDB, `utf8mb4_unicode_ci`, clés étrangères, noms en français, clés `id_<entité>`.
- Chaque action sensible (connexion, création, modification, suppression) est journalisée par `$U->audit()`, avec sa cible quand elle porte sur un objet (`'user'`, `'contact'`).
- Toute écriture sur un dossier passe par `$Contact->tracer()`, dans la même transaction que la donnée : journal d'audit, et chronologie (`d_evenement`) pour les faits qu'un utilisateur doit lire. Ni l'un ni l'autre ne reçoit de valeur de champ : noms de champs, identifiants, codes.
- `d_contact.statut` ne s'écrit que par `$Contact->changerStatut()` ; les ventes (premier paiement) et les rendez-vous (demande, créneau à venir) l'appellent avec l'origine `automatique`. Un automatisme ne fait jamais reculer un statut : il le propose (`proposition`).
- Suivi : toute écriture sur un dossier se fait sous `$Contact->verrouiller()`. `r_rdv.statut` ne s'écrit que par `Rdv::changerStatut()` et `Rdv::replanifier()` ; `r_rdv.date_debut` ne se modifie pas une fois fixé (un déplacement crée une ligne chaînée). `d_contact.date_derniere_interaction` ne s'écrit que par `Interaction::recalculerDerniere()`. Une tâche automatique ne se crée ni ne se ferme hors de `Tache::synchroniser()`, qui reste silencieuse (ni audit, ni chronologie) et ne dépend jamais de l'utilisateur qui lit.
- Textes internes du suivi (motif, raison, compte rendu, intitulé d'une tâche de suivi) : servis avec le droit `famille` seulement (`sortie($ligne, $avecTextes)`, `Tache::lisible()`), jamais dans `u_audit` ni dans `d_evenement.details`. Le profil `gestion` lit l'agenda sans textes, aucun échange, et les seules tâches de gestion.
- L'instant et le jour utilisés dans une comparaison viennent de PHP (`date()`, fuseau Europe/Paris) et sont servis au front (`aujourdhui`, `passe`, `commence`, `situation`) : le front affiche, il ne déduit pas. La session MySQL est réglée sur le même fuseau à la connexion (`Mysql::OuvrirBase()`).
- Finances : montants en centimes entiers (colonnes `INT` signées avec `CHECK`, pour que les soustractions SQL ne débordent pas) ; `v_paiement` est la seule source des sommes, lues par le fragment `Vente::SQL_SOMMES` (les totaux d'une liste se calculent avec le même `WHERE` que ses lignes) ; `v_vente.statut` et les caches de `v_echeance` ne s'écrivent que dans `Vente::recalculer()` ; une écriture ne se supprime jamais (annulation tracée ou écriture contraire) ; chaque écriture financière verrouille le dossier (`Contact::verrouiller()`) et fait ses contrôles de saisie avant d'ouvrir la transaction ; le « jour » d'un retard vient de PHP (`date('Y-m-d')`), jamais de `CURDATE()`.
- Tableau de bord : un chiffre est le total de la liste qu'il ouvre (CDC §27). Les totaux d'une sélection ne s'écrivent que dans `Vente::totauxVentes()`, `totauxJournal()` et `totauxEcheances()`, appelées par les listes et par `Pilotage` avec le même `WHERE` ; les dossiers se comptent avec les conditions de `v1/contacts/` (`Contact::SQL_ARRIVEE` pour la date d'arrivée). Ajouter un chiffre, c'est d'abord savoir quelle liste le reproduit, puis l'écrire dans la batterie de contrôles.
- Activité récente (`Contact::activite()`) : liste blanche `Contact::SQL_ACTIVITE`, aucun texte, aucun libellé familial. Un nouveau type de fait n'y entre que si on l'y ajoute. La mise en forme d'un fait (`faitSortie()`) est partagée avec `chronologie()`, qui seule lit les textes, avec le droit `famille`.
- Valeurs avant / après d'un changement financier : dans `v_historique` uniquement. Ni `u_audit` ni `d_evenement` ne reçoivent de montant ; la chronologie joint le montant à la lecture (clé `objet`).
- Les automatismes du dossier (`Vente::automatismes()`) changent le statut d'un dossier pour le compte d'un profil qui n'a que la lecture sur les dossiers (`gestion`) : c'est voulu, l'écriture financière en est la cause.
- Stripe : un événement n'est qu'un **signal** (type et identifiant) ; l'objet est toujours relu chez Stripe avant d'écrire. Un seul traitement, `PaiementStripe::constater()`, pour les quatre sources (webhook signé, rattrapage, page de retour, issue d'un prélèvement), qui écrit par `Vente::creer()` et `Vente::ecrire()` avec l'origine `automatique`. Tout fait est rejouable : l'idempotence tient au `stripe_id`, contrôlé sous le verrou du dossier. **Jamais de verrou de dossier ni de transaction ouverte pendant un appel à Stripe** : la création d'une page de paiement est sérialisée par `GET_LOCK`, et une vente n'a qu'une session ouverte. Un fait qui ne peut pas s'écrire reste « en erreur » dans `s_evenement`, visible et relançable depuis l'onglet « Connexions ». Aucune donnée de carte n'est stockée, seulement des identifiants Stripe. Une clé de test est refusée quand `$_PROD = 1`, une clé réelle quand `$_PROD = 0`. Le webhook exige sa signature, sans repli.
- Achat en ligne : la vente n'est créée qu'au paiement (une commande abandonnée reste dans `s_commande`). Un dossier existant n'est jamais modifié par un achat (l'identité déclarée reste dans la commande) et la réponse d'un endpoint public ne dit rien d'un dossier.
- Prélèvements : jamais avant la date de l'échéance, ni moins de `$_PRELEVEMENT_AVIS_JOURS` jours après l'e-mail d'avis, ni hors de `$_PRELEVEMENT_HEURES` ; `$_STRIPE_PRELEVEMENTS = 0` les coupe tous. La ligne `s_prelevement` s'insère avant l'appel et sert de clé d'idempotence ; un prélèvement resté « en cours » se résout en relisant Stripe, jamais en rejouant l'appel. Pas de nouvelle tentative automatique après un échec : tâche « paiement échoué », e-mail au parent avec un lien, et la main à l'utilisateur (relancer, suspendre, reprendre). Un remboursement se fait dans Stripe : l'outil le constate et l'écrit.
- E-mails : tout envoi passe par `Message::deposer()`. En mode `essai`, rien ne sort du serveur. Le corps conservé ne contient jamais de jeton : la marque `{{lien_paiement}}` est remplacée au moment de l'envoi. Un envoi laisse le fait `email` dans le fil du dossier (le modèle seulement, aucun texte) ; il n'entre pas dans l'activité récente. L'e-mail « nouvelle semaine » reste éteint tant que `$_APP_PARENTS_URL` est vide.
- Compte et programme : `a_compte` ne s'écrit que par `Compte`. « Terminé » ne se stocke pas, il se déduit de `date_fin` à la lecture, avec `Compte::conditionVue()` partout. Le programme servi (`etat`, `semaine`, `sur`, `fin_proche`) est calculé par PHP : le front l'affiche. La base `navup` est aussi celle de l'appli des parents : `f_*` et `a_compte` sont ses sources de vérité.
- Formation : un sujet ne se publie qu'avec son audio prêt et sa fiche ; un sujet publié ne se supprime pas. Les fichiers ne se lisent que par `v1/formation/fichier/`, authentifié. Type vérifié par `finfo`, jamais par le nom. Toute commande `ffmpeg` passe ses chemins par `escapeshellarg`.
- **Appli des parents** (`/var/www/navup-parent-api`) : elle lit cette base avec un utilisateur MariaDB restreint, et **la base est le contrat**. Ce qui décide de l'accès s'écrit ici, dans `a_compte` (état, `date_debut`, `date_fin`, `date_fin_acces`, `date_revocation`) ; l'appli le lit par la vue `a_acces`, et le jour où chaque semaine se débloque par la vue `a_semaine` (changer la règle de déblocage, c'est changer cette vue et `Compte::programme()` ensemble : `verifier-connexions.php` les compare). `date_fin` reste la fin du programme (statut, alerte « fin proche ») ; `date_fin_acces` (≥ `date_fin`, posée à `date_fin + $_ACCES_APRES_FIN_JOURS`) est la fin de la consultation. Un lien d'accès ne se crée que par `Compte::lienAcces()`, au moment de l'envoi d'un e-mail (marque `{{lien_acces}}`) ou à la demande d'un utilisateur ; il porte son jeton dans le fragment de l'adresse et seule son empreinte est gardée. `Compte::revoquer()` (e-mail du dossier modifié, geste « Réinitialiser l'accès ») rend nuls les sessions, le mot de passe et les liens antérieurs. Les tables `e_*` appartiennent à l'appli : cette API les lit (`Compte::acces()`, `annoncerSemaines()`), les purge (passe `taches`, `purge-essais.php`), n'y écrit jamais. Une fiche n'est prête qu'avec ses pages rendues en images (`Formation::rendrePages()`, noms `<empreinte>.p<N>.jpg`) : c'est ce que l'appli affiche sur un téléphone.
- **Rendez-vous en ligne** (étape 6b) :
  - Un seul chemin d'écriture : la page publique, l'espace des parents et l'outil écrivent par `Rdv` ; les gestes d'un parent laissent un fait d'origine `parent` et un avis interne au responsable (`rdv_avis`, hors du fil du dossier).
  - Ordre des verrous, partout : adresse e-mail (`navup_commande_<sha1>`, le même que l'achat), agenda (`Rdv::prendreAgenda()`, pris **avant** la transaction, rendu après), dossier. L'outil prend aussi le verrou d'agenda ; il avertit d'un chevauchement, il ne le refuse pas.
  - Un créneau ne se réserve que par `Agenda::attribuer()` : durée et type viennent de `$_RDV_PRISE`, jamais du corps d'une requête. « Créneau pris » se décide avant toute lecture de dossier.
  - Un endpoint public de rendez-vous ne dit rien d'un dossier : réponse unique `{suite: "email"}`, aucun message d'une classe métier ne sort (il s'écrit dans le journal du serveur). Son e-mail dit « Bonjour, » et ne recopie rien de la saisie.
  - Le parent n'est prévenu que d'un créneau **confirmé** (`r_rdv.prevenir` garde le choix de la case). Les e-mails se déposent dans la transaction du fait ; avant l'envoi, `Message::perime()` annule (état `annule`) un message dont le rendez-vous ne tient plus ou dont l'adresse du dossier a changé.
  - Chaîne d'un rendez-vous déplacé : `id_rdv_origine` et `rang`, écrits à l'insertion. Le lien de gestion (`r_lien`), ce que le parent a déclaré (`r_reservation`, jamais modifié, note avec le droit `famille`) et l'identifiant de l'invitation s'y rattachent.
  - Jetons (lien de gestion, flux d'agenda, billet) : empreinte seule en base. Le lien de gestion et le billet voyagent dans un fragment d'adresse et le corps d'une requête ; le flux d'agenda a son jeton dans l'adresse (un calendrier ne sait rien envoyer d'autre) : il ne sert ni nom complet, ni téléphone, ni note.
  - Parent inscrit : l'API des parents écrit un billet dans `e_billet` (elle n'y a que le droit `INSERT`), cette API le lit et revérifie la session et le compte. Aucun secret partagé, aucune règle de rendez-vous recopiée chez elle.
  - Pas d'invitation à l'annulation, pas de réponse attendue du parent à une invitation, pas de synchronisation dans les deux sens : un créneau occupé ailleurs se ferme par une absence.
- **Paramètres** (étape 7b) : réservés à l'administrateur (`parametres` complet), chaque changement au journal d'audit (`reglage_update` avec avant et après, `liste_create`, `liste_update`, `modele_email_update`, `modele_email_retablir` avec le seul numéro de version). Un nouveau réglage s'ajoute à `param.php` (sa valeur par défaut) **et** au catalogue de `Reglage`, avec ses bornes ; aucun code ne lit `p_reglage` directement. Une valeur de liste de référence ne se supprime jamais : elle se désactive. Types de rendez-vous et statuts ne sont pas réglables (ils commandent des règles).
- **Alertes** : une alerte s'allume ou s'éteint (`$_ALERTES_ACTIVES`) ; éteinte, ses tâches ouvertes se ferment « sans objet » ; rallumée, elles se rouvrent. Une nouvelle alerte s'ajoute à `Tache::ALERTES`, à `causes()`, au catalogue de `Reglage` et à `ALERTE_LABELS` du front.
- **Modèles d'e-mails** : un texte enregistré passe `Modeles::controler()` (marques connues, blocs et liens présents, objet sans bloc) ; chaque message garde sa version (`m_message.version_modele`). Un gabarit d'origine ne se modifie que si `verifier-emails.php` prouve qu'il rend toujours le même e-mail.
- **Statistiques et exports** (étape 7a) : un chiffre des statistiques est le total d'une liste, calculé par `Pilotage` avec la requête de cette liste ; les parts (longueurs de barres) sont calculées ici, jamais dans le front. Une catégorie de problématique sous `Pilotage::SEUIL_PROBLEMATIQUE` dossiers n'est pas chiffrée. Un export ne recopie aucune requête (voir `Export`) ; il ne sort que ce que la liste sert déjà (jamais de donnée familiale ni de note interne sans droit), n'est jamais gardé, et son nom ne contient aucune donnée de dossier. Le journal d'audit ne s'exporte que pour l'administrateur. Pas de clôture de période ni de facture : en attente des exigences comptables.
- Tâche planifiée : chaque passe est rejouable sans effet, compte ses essais par élément (écarté au-delà de cinq) et rend une ligne de compte rendu ; une nouvelle passe s'ajoute à la liste de `planifie.php` et à `Connexions::planifie()`.
- Les ventes ne partent pas en cascade avec un dossier (`ON DELETE RESTRICT`) : tout script qui supprime un dossier efface d'abord ses ventes, ou les conserve (effacement RGPD, étape 8).
- Colonnes d'un dossier servies par liste explicite (`Contact::COLONNES`), jamais `c.*` : une colonne ajoutée ne doit pas sortir par accident.
- Aucune donnée personnelle dans un mail d'erreur ni dans un journal technique.
- Messages d'erreur destinés à l'utilisateur en français.
- Une erreur métier sur un utilisateur déjà authentifié répond **400**, jamais 401 : le front vide la session sur tout 401.
- Un endpoint qui renvoie un fichier garde `$H->cors('json')` puis remplace `Content-Type` avant `echo`.
- Données familiales (module `famille`) : `d_contact` n'en contient aucune ; jamais renvoyées par un endpoint de liste ou de recherche ; les endpoints qui les servent appellent `$Contact->exigerFamille()`. Un filtre qui révèle une donnée familiale répond 403 sans ce droit (jamais ignoré en silence). La provenance de chaque donnée est conservée (colonne `source` : `saisie_navup` ou `formulaire`), les notes internes sont à part (`d_note`).

- **Double authentification** (étape 8) : `Totp` (aucune librairie). Le secret est chiffré par `$_CLE_TOTP` ; un code ne sert qu'une fois (`totp_dernier_pas`, condition dans l'`UPDATE`) ; un code faux compte comme un mot de passe faux, et le mot de passe juste ne remet pas le compteur à zéro tant que le code n'est pas donné. Les codes de secours ne sont gardés qu'en empreinte HMAC.
- **RGPD** (étape 8) : un effacement passe par `Rgpd::effacer()` et rien d'autre ; une nouvelle table qui porte une donnée de dossier s'y ajoute (et à `Rgpd::exporter()` si le parent l'a donnée), et `verifier-rgpd.php` la cherche alors d'elle-même (toutes les colonnes de texte). Un dossier anonymisé en entier refuse toute écriture web (`Contact::verrouiller`). Le journal ne garde que le fait et le degré.
- **Sauvegardes** : `Sauvegarde` (archive chiffrée par `$_CLE_SAUVEGARDE`, manifeste scellé par HMAC, vérifié avant tout déchiffrement) ; une restauration ne vise jamais la base en service. `NAVUP_BASE` (ligne de commande seulement) fait tourner les scripts de contrôle sur la base de test.

## Profils et droits

`admin`, `accompagnement`, `gestion` — un seul profil par utilisateur ; toujours au moins un admin actif ; verrouillage 15 min après 5 échecs de connexion ; mot de passe de 12 caractères minimum avec majuscule, chiffre et caractère spécial. La matrice (`User::MATRICE`) est dupliquée dans `navup-front/src/app/core/rbac.ts` : modifier les deux ensemble.

## Tests manuels

Voir `README.md` (installation, création de l'admin, commandes curl). Les contrôles dans le navigateur sont dans `navup-front/outils/` ; ils nettoient derrière eux avec `script-cgi/purge-essais.php` (comptes `essai.*`, dossiers en `essai.…@navup.local` avec leurs ventes, rendez-vous, échanges et tâches, tâches sans dossier dont la clé de saisie commence par `e55a1e55-`, refusé en production), et vérifient avant la purge les finances (`script-cgi/verifier-finances.php`) et le suivi (`script-cgi/synchroniser-taches.php` puis `script-cgi/verifier-suivi.php`).

Étape 6a : `php script-cgi/verifier-connexions.php` (lecture seule : signaux, e-mails, comptes, commandes, fichiers de la formation, tâche planifiée) ; `php script-cgi/essai-stripe.php` (scénario complet contre le vrai Stripe en mode test, refusé sans clé de test) ; `php script-cgi/importer-formation.php --dossier=…` (charge la formation fournie par le client, rejouable). Sur ce poste, php-fpm ne joint Stripe que si SELinux l'y autorise : `sudo setsebool -P httpd_can_network_connect 1`.

Étape 7b : `php script-cgi/verifier-emails.php` (lecture seule : chaque gabarit d'origine rend l'e-mail d'avant, sur 44 variantes ; chaque version active passe le contrôle) ; `php script-cgi/essai-alertes.php --email=essai.…@navup.local [--vieillir=N] [--fin-acces=N] [--programme-debut=-N]` (poste de développement : place un dossier d'essai dans la situation d'une alerte).

Étape 7a : `php script-cgi/verifier-statistiques.php` (lecture seule : les répartitions redonnent leurs totaux sur chaque période, le classeur et le rapport se fabriquent ; l'égalité de chaque chiffre avec sa liste se contrôle dans `navup-front`, `npm run parcours`).

Étape 6b : `php script-cgi/essai-rdv.php` (scénario complet des rendez-vous en ligne, contrôlé ligne par ligne, sans rien envoyer : réservation, rejeu, double réservation, créneau forgé, lien, déplacement, annulation, message périmé, rappel, changement d'heure ; `--montrer` affiche l'e-mail tel qu'il partirait ; `--disponibilites=essai.agenda` et `--reserver=<e-mail>` préparent un essai dans un navigateur), refusé en production.

Appli des parents : `php script-cgi/essai-parent.php` (un parent d'essai placé où l'on veut dans son programme, et son lien d'accès), `php script-cgi/essai-publication.php --publier=1-11 | --retablir` (publie des sujets pour le temps d'un contrôle), tous deux refusés en production ; `php script-cgi/rendre-fiches.php` (pages des fiches déjà rangées) ; `php script-cgi/inviter-comptes.php [--simuler]` (campagne d'invitation des comptes sans accès). Les parcours du front des parents (`navup-parent-front/outils/`) n'ont besoin d'aucun identifiant.
